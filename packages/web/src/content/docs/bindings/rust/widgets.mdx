# Widgets and layout

An app is a tree of widgets under `app.root()`.
This page covers how you create and change widgets, how layout sizes them, which widgets exist, and where their default colors come from.

## Create and change widgets

You create a widget with `new` and set its properties with chained methods.
The same methods change it later, for example from an event handler:

```rust
let status = Text::new(&app, "Ready").fg(Color::GREEN).bold();
// Later, from an event handler:
status.set_text("Saved").fg(Color::CYAN);
```

A widget value is a handle: cloning it is cheap, and every clone refers to the same widget.
Property methods take `&self` and return the handle, so you can chain them on a widget that is already on screen.
Each change takes effect at once and schedules a frame.
The app draws a frame only when something changed, and at most `AppOptions::max_fps` times per second.

A parent keeps its children alive.
A widget that is not attached to the tree is destroyed when its last handle drops.
Handlers can capture widget handles, including their own widget's, without leaking: the app breaks those reference cycles when it ends.

Setters do not return `Result`.
If the native library rejects a change, such as an infinite width, the app records the error.
`App::run` restores the terminal and returns the error at the end of that event loop turn.

## Layout

Layout is flexbox.
Lengths are in terminal cells: integers convert to lengths, and `Length::percent(50.0)` gives a percentage.

`grow(n)` works like CSS `flex: n`.
The widget fills the free space, shared with its growing siblings in proportion to their factors, whatever its content.
Widgets without `grow` size to their content.
When content outgrows its space, the widget scrolls or clips instead of pushing its siblings away.

Scrolling widgets (`ScrollBox`, `Select`, `Table`, and `Code`) need a height or a grow factor, or they have no room to show.

The `Widget` trait has the layout methods:

- size: `width`, `height`, `min_width`, `min_height`, `max_width`, `max_height`, `aspect_ratio`, `box_sizing`, and `grow`
- direction and spacing: `row`, `column`, `gap`, and the `padding*` and `margin*` methods
- alignment: `justify` and `align_items`
- placement: `absolute` with `position`, and `visible`

## Fragments

A `Fragment` groups widgets without adding a box.
Its children lay out, draw, take focus, and receive clicks as children of the fragment's parent, at the fragment's position:

```rust
let extras = Fragment::new(&app).child(&Text::new(&app, "b")).child(&Text::new(&app, "c"));
let row = View::new(&app).row().child(&Text::new(&app, "a")).child(&extras).child(&Text::new(&app, "d"));
// The row shows "abcd".
```

The parent holds the fragment as one child.
`insert`, `detach`, and adding it to another parent move all of its children together, and you can add children to the fragment before or after it is attached.
Fragments nest, and an empty fragment takes no space.
Keys and mouse events bubble from its children through the fragment's handlers to its parent.

A fragment has no geometry: its `rect` is empty, and the layout, paint, filter, `visible`, `focusable`, `on_click`, and `on_resize` methods do nothing on it, and neither does `ScrollBox::scroll_into_view(&fragment)`.
Use its children instead.

## Slots

`opentui::slot` lets plugins add widgets to places that the app names, as Core's [slot tree](/docs/extend/runtime-plugins#nested-slots) does.
A slot path is names joined by dots, and a path contains every path that extends it at a dot.
A `slot::Tree<I, M>` holds the owners, their claims, and the mounted slots.
`I` is a slot's input, and `M` is what a claim's render returns, `AnyWidget` by default.

```rust
use opentui::slot::{Placement, Tree};

let tree = Tree::<String>::new();
let clock = tree.owner("clock");
clock.claim(Placement::append("footer.status"), |app, _, _| Text::new(app, " 12:00").as_any())?;
clock.claim(Placement::before("footer"), |app, user: &String, _| Text::new(app, user.clone()).as_any())?;

let footer = tree.mount(&app, "footer", "ava".to_owned());
let status = footer.mount("footer.status", String::new())?;
status.content().add(&Text::new(&app, "ready"));
footer.content().add(&status);
app.root().add(&footer);
```

`tree.mount` returns a `Slot`, a widget with no box of its own, like a `Fragment`.
It shows the claims before it, then the replacing claim or the prepended claims, its `content()` and the appended claims, then the claims after it.
The path stays mounted while one of its slots lives.

`slot.mount` nests a slot whose path extends the slot's, or returns `MountError::NotContained`.
A render gets a `WeakSlot`, so a mount can nest slots after the render returns; once the slot is gone, `WeakSlot::mount` returns `MountError::Unmounted`.
A path with an empty name, such as `footer..status`, makes `owner.claim`, `slot.mount`, and `WeakSlot::mount` return `MountError::InvalidPath`, so a plugin's mistyped path fails only its own claim.
The host's own `tree.mount` panics on one, as a programming error.

The claims resolve as in Core: in owner order, then in the order each owner made them, and `tree.order(ids)` sets the owner order.
For each target the last replacement wins and suppresses every claim inside it.
A claim on a path that is not mounted appends to its nearest mounted ancestor.
`tree.resolution()` lists the placed, suppressed, and degraded claims, and `slot::resolve` computes the same without a tree.
`owner.unclaim(id)` removes one claim, `owner.reset()` drops all of them and keeps the owner's place, and `owner.remove()` forgets the owner.

A render can return an app type that implements `Mount<I>`: `root()` gives the widget, and `set_input` takes a new input in place, or returns `false` to render the claim again.
`slot.set_input` gives every claim of the slot a new input, and `slot.each` visits the mounted claims.

A change made through a slot, such as `tree.mount` or `slot.set_input`, or inside `tree.batch`, shows when the call returns.
Any other change, such as a claim, a reset, or the last slot of a path dropping, shows at a settle that the tree defers to the app before the next frame.
`tree.settle()` shows it at once.
A claim that still shows keeps its mount.

## Themes

Widgets take their default colors from the app's `Theme` when you create them.
`App::new` asks the terminal for its background color and picks `Theme::dark()` or `Theme::light()` to match.
To choose instead, set a theme with `AppOptions::with_theme`.
`Theme::terminal()` is a theme that uses the terminal's own colors.

When the system switches between dark and light mode, the app calls your `App::on_theme_mode` handlers.
In the handler, call `App::set_theme`.
It changes the background, the colors that new widgets start with, and the selection colors of every widget, current selections included.
A widget's own `selection_colors` win per color: a color it leaves `None` takes the theme's, so a selection inverts its cells only when neither sets a background.
Existing widgets keep their other colors, so the handler also recolors or rebuilds them.

Set `AppOptions::palette_size` to also read the terminal's color palette, which `App::palette` returns.
On terminals without true color, the renderer uses the palette to pick the closest colors.
