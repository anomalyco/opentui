# Rust keymap

`opentui::keymap` ports [`@opentui/keymap`](/docs/keymap/overview) to Rust: layered bindings, named commands, multi-key sequences, tokens such as `<leader>`, and runtime conditions such as modes.
It is pure Rust. It does not call the native library and does not own an event loop.
The app feeds it key events, focus, and time, and it reports whether each key was consumed.

This keymap is not the per-widget `Keymap` in the prelude, which maps keys to a widget's actions (see [Widget key bindings](/docs/bindings/rust/input#widget-key-bindings)).

```rust
use opentui::input::{KeyCode, KeyEvent, Modifiers};
use opentui::keymap::{Binding, Command, Keymap, Layer};
use std::cell::Cell;
use std::rc::Rc;

let keymap = Keymap::<u32>::new();
let saved = Rc::new(Cell::new(0));
let counter = saved.clone();
let layer = keymap.register_layer(
    Layer::new()
        .command(Command::new("file.save", move |_| counter.set(counter.get() + 1)))
        .binding(Binding::new("ctrl+s").cmd("file.save")),
);
let result = keymap.handle_key(&KeyEvent::new(KeyCode::Char('s'), Modifiers::CTRL));
assert!(result.handled);
assert_eq!(saved.get(), 1);
drop(layer);
assert!(!keymap.handle_key(&KeyEvent::new(KeyCode::Char('s'), Modifiers::CTRL)).handled);
```

Each registration returns a `Disposer`. Dropping it undoes the registration; `Disposer::forget` keeps it for as long as the keymap lives.

## Model

The Rust engine keeps the TypeScript engine's data model and dispatch rules, so key sequences resolve to the same commands.

- A `Keymap<T>` is a cheap-to-clone handle to shared state. `T` identifies focus targets, such as a widget id. Commands, conditions, and intercepts are closures that may call back into the keymap (set data, register layers, dispatch a command) while a key is dispatched; the engine never holds its internal borrow across a callback.
- A `Layer<T>` has an optional `target` and `TargetMode` (`FocusWithin` by default, or `Focus`), a `priority`, an `enabled` condition, data requirements (`require("mode", "base")`), `bindings`, and `commands`. Layers sort by priority, then newest first, as in TypeScript.
- A `Binding<T>` has a key (`"ctrl+x"`, `"<leader>n"`, `"gg"`, or a `Stroke`), a command (a command name or an inline handler), `press` or `release`, `prevent_default` (default true), `fallthrough` (default false), and the metadata fields `desc` and `group`.
- A `Command<T>` has a name, a handler that returns handled or rejected, the metadata fields `title`, `desc`, `category`, and `namespace`, an `enabled` condition, and an opaque `data` value for the app.
- A string binding command is visible only while a command of that name is reachable: registered in an active, enabled layer. The first reachable command of a name wins; a rejected command falls through to the next one of the same name.

Focus comes from the app: `set_focus(path)` takes the focused target followed by its ancestors.
A focus change clears a pending sequence, as the TypeScript host's focus event does.

Dispatch runs key intercepts by priority first.
With a pending sequence, the captures advance and the best match wins.
Otherwise each layer in order either starts a sequence or runs its exact bindings; a prefix collects continuations from every lower layer too.
An exact binding and a prefix in different layers resolve to the prefix, as in TypeScript; in one layer they are a compile error.
A key that does not continue a pending sequence clears it and is not consumed.

## API

| `@opentui/keymap`                                                                        | `opentui::keymap`                                                                                           |
| ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `createDefaultOpenTuiKeymap(renderer)`                                                   | `Keymap::new()`: default parser, default event matcher, `enabled` and metadata fields built in              |
| `registerLayer(layer)`                                                                   | `keymap.register_layer(layer) -> Disposer`; dropping the `Disposer` unregisters, `forget()` keeps the layer |
| `registerLayerFields({ mode })` + `setData`                                              | `Layer::require(name, value)` + `keymap.set_data(name, value)`                                              |
| `registerToken`, `registerLeader`                                                        | `keymap.register_token(name, key)`, `addons::leader`                                                        |
| `appendBindingExpander`                                                                  | `keymap.append_binding_expander(f)`                                                                         |
| `appendEventMatchResolver`                                                               | `keymap.append_event_match_resolver(f)`                                                                     |
| `intercept("key", f, { priority, release })`                                             | `keymap.intercept_key(priority, release, f)`                                                                |
| host key listener                                                                        | `keymap.handle_key(&KeyEvent) -> KeyResult`                                                                 |
| host focus listener                                                                      | `keymap.set_focus(path)`                                                                                    |
| `dispatchCommand`, `runCommand`                                                          | `keymap.dispatch_command(name)`, `keymap.run_command(name)`                                                 |
| `getCommands`, `getCommandEntries`, `getCommandBindings`                                 | `commands(query)`, `command_entries(query)`, `command_bindings(visibility, names)`                          |
| `getPendingSequence`, `hasPendingSequence`, `clearPendingSequence`, `popPendingSequence` | same names in snake case                                                                                    |
| `getActiveKeys({ includeBindings, includeMetadata })`                                    | `active_keys(options)`                                                                                      |
| `createKeyMatcher`, `parseKeySequence`, `formatKey`                                      | `parse_key` (compare its `stroke`), `parse_key_sequence`, `format_key`                                      |
| a binding key as `registerLayer` expands it (no TypeScript call)                         | `parse_binding`: binding expanders, then one sequence per expanded key                                      |
| `on("state")`, `on("pendingSequence")`, `on("warning" / "error")`                        | `on_state`, `on_pending_sequence`, `on_diagnostic`; `revision()` counts state changes                       |
| `stringifyKeyStroke`                                                                     | `Stroke`'s `Display`                                                                                        |
| extras `createBindingLookup`                                                             | `extras::BindingLookup`                                                                                     |
| extras `formatKeySequence`, `formatCommandBindings`                                      | `extras::format_key_sequence`, `extras::format_command_bindings`                                            |

`Stroke::from_event` maps an `opentui::input::KeyEvent` to Core's key names: `return`, `escape`, `pageup`, Shift+letter as `shift` plus the lower-case letter, and Alt or Meta as `meta`.
Binding strings mean what they mean in TypeScript.

## Not ported

These parts of `@opentui/keymap` have no Rust equivalent:

- sequence patterns (`{count}`)
- disambiguation resolvers and command resolvers
- binding, layer-bindings, and command transformers
- custom binding parsers and custom field compilers; typed fields replace the compilers
- `key:after` and raw intercepts
- layer analyzers
- the graph and HTML extras
- the Solid and React adapters

Commands are synchronous, so async results and their errors do not apply.
A binding that uses an unregistered `{pattern}` is skipped with an unknown-token warning, as TypeScript does when the pattern is missing.
