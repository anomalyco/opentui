# Install, link, and ship

The crates link OpenTUI's native library. They do not build it.
An app gets the library from a GitHub release, or from a native build of a checkout of the repository.

The crates are not on crates.io.
They use Rust's 2024 edition (Rust 1.85 or later) and declare no other minimum Rust version; CI builds them with Rust 1.99.1.
They carry the version of `@opentui/core`, and each release of OpenTUI tags them with it.

## Depend on a release

1. Add the crates as a Cargo `git` dependency, pinned to a release tag:

   ```toml
   [dependencies.opentui]
   git = "https://github.com/anomalyco/opentui"
   tag = "v0.9.3"
   ```

   Add `opentui-ssh` the same way to serve apps over SSH.

2. Download the native archive for the target from that release's assets on [GitHub Releases](https://github.com/anomalyco/opentui/releases), for example `opentui-native-v0.9.3-linux-x64.zip`.
   The archive has no top-level folder: extract it into its own directory, such as `vendor/opentui-native`.
   It holds `opentui.h`, the shared and static libraries, and the licence notices.

3. Set `OPENTUI_LIB_DIR` to that directory when you run Cargo.
   Give an absolute path: Cargo reads a relative one from the `opentui-sys` crate's directory.
   A project can set it in `.cargo/config.toml`, where `relative = true` makes the path absolute.
   `OPENTUI_LIB_HINT` names the project's own setup step; `scripts/fetch-opentui.sh` here is an example:

   ```toml
   [env]
   OPENTUI_LIB_DIR = { value = "vendor/opentui-native", relative = true }
   OPENTUI_LIB_HINT = "run scripts/fetch-opentui.sh"
   ```

A release archive fits only a dependency pinned to that release's tag.
Any other commit needs a native build of that commit.

When a file is missing, the build fails and says which release archive to extract.
With `OPENTUI_LIB_HINT` set, it prints that text instead, so a project can name its own setup step.

## Build from a checkout

In a checkout, the crates link `lib/<artifact directory>` in the native workspace of that checkout.
Build the native library first, then run Cargo from the repository root:

```sh
bun install
bun run build   # or `bun run build:native` in packages/core
cargo test --manifest-path packages/rust/Cargo.toml
```

`OPENTUI_LIB_DIR` wins over the checkout's build.
It can name a release archive's directory, or the directory of an npm platform package such as `node_modules/@opentui/core-linux-x64`.
An npm platform package ships only the shared library, so it needs the [default features off](#static-and-shared-linking), except with the Windows GNU targets.

The macOS build needs the macOS SDK, which comes with the Xcode Command Line Tools (`xcode-select --install`).
On a Mac, `bun run build` in the native workspace builds the Mac's own architecture.
Add the other one with `zig build -Doptimize=ReleaseFast -Dlibrary-target=x86_64-macos.13.0` (or `aarch64-macos.13.0`).
The Windows build needs no SDK, so Zig makes it on any system: `zig build -Doptimize=ReleaseFast -Dlibrary-target=x86_64-windows-gnu`.

## Platforms

| Platform                       | Rust target                                             | Release archive    | Artifact directory   |
| ------------------------------ | ------------------------------------------------------- | ------------------ | -------------------- |
| Linux x86_64 with glibc        | `x86_64-unknown-linux-gnu`                              | `linux-x64`        | `x86_64-linux`       |
| Linux arm64 with glibc         | `aarch64-unknown-linux-gnu`                             | `linux-arm64`      | `aarch64-linux`      |
| Linux x86_64 with musl         | `x86_64-unknown-linux-musl`                             | `linux-x64-musl`   | `x86_64-linux-musl`  |
| Linux arm64 with musl          | `aarch64-unknown-linux-musl`                            | `linux-arm64-musl` | `aarch64-linux-musl` |
| macOS 13 or later, Apple chips | `aarch64-apple-darwin`                                  | `darwin-arm64`     | `aarch64-macos`      |
| macOS 13 or later, Intel chips | `x86_64-apple-darwin`                                   | `darwin-x64`       | `x86_64-macos`       |
| Windows 10 1809 or later       | `x86_64-pc-windows-msvc`, `x86_64-pc-windows-gnu`       | `windows-x64`      | `x86_64-windows`     |
| Windows 10 1809 or later, Arm  | `aarch64-pc-windows-msvc`, `aarch64-pc-windows-gnullvm` | `windows-arm64`    | `aarch64-windows`    |

The release archive is `opentui-native-v<version>-<release archive>.zip`.
A checkout builds into `lib/<artifact directory>` in the native workspace.
The build picks the directory for the target it builds.

Rust's musl targets build static executables (`crt-static`), which cannot load `libopentui.so`.
The build refuses the shared library there: keep the default `static` feature, or turn the default features off and build with `RUSTFLAGS='-C target-feature=-crt-static'`.

## Generated bindings

`src/generated.rs` in `opentui-sys` is generated from the native workspace's `include/opentui.h`.
`bun run generate:abi` in the core package writes it, and `bun run check:abi` fails when it is stale. Do not edit it.
The bindings are valid only for the exact header they were generated from.
The build fails if the artifacts' header differs.

## Features

- `static` (default): link the static library. See [Static and shared linking](#static-and-shared-linking).
- `tokio`: `App::spawn` runs futures on a Tokio runtime and finishes them on the UI thread.
- `log`: `console::init_logger` shows the `log` crate's records in the debug console.
- `tree-sitter`: `Code`, `Diff`, `Textarea`, and Markdown code blocks highlight with tree-sitter. It bundles Core's grammars (JavaScript, TypeScript and TSX, Markdown, Zig) and Rust. The checkout's `run.sh` turns it on.

## Static and shared linking

By default the crate links `libopentui.a` on Linux and macOS, and `opentui-static.lib` on the Windows MSVC targets.
An executable then needs no OpenTUI file at run time, and on Linux no libc++ either.

- On Linux the archive carries its own libc++, so the program needs only libc. That libc++ is private to OpenTUI, so C++ code elsewhere in the program keeps its own runtime, libstdc++ or libc++, shared or static.
- On macOS the feature also links the system frameworks OpenTUI uses for the clipboard, audio, and video.
- On the Windows MSVC targets, `opentui-static.lib` is built for MinGW and carries the parts of MinGW's runtime that MSVC lacks, among them libc++, so C++ code elsewhere in the program keeps MSVC's runtime. Built with `RUSTFLAGS='-C target-feature=+crt-static'`, the `.exe` needs no Visual C++ runtime DLL either, so it is the only file to ship.
- The Windows GNU targets link `opentui.dll` with or without the feature: their own MinGW runtimes are not the one the archive was built for.

The Windows GNU targets, and the MSVC targets without the `static` feature, link `opentui.dll` through its import library `opentui.lib`.
Ship `opentui.dll` beside the `.exe`. The build copies it where `cargo run` and `cargo test` find it.

To link `libopentui.so`, `libopentui.dylib`, or `opentui.dll` instead, turn the default features off (`default-features = false`, or `--no-default-features`).
Cargo merges features across the app's graph, so every crate in it that depends on `opentui` must turn them off.
The workspace's tests and examples find the library through an rpath.
Other executables need their own rpath, `LD_LIBRARY_PATH` on Linux, or `DYLD_LIBRARY_PATH` on macOS.

## Video and licences

`VideoView` needs a library built with FFmpeg.
The native build links it from `.cache/ffmpeg/prefix/<target>` in the native workspace, which `bun run build` makes for the host.
Without it, the build warns and leaves video out.

The default native library includes FFmpeg under LGPL-2.1-or-later, even if your app never uses `VideoView`.
`opentui-sys` ships `LICENSE-FFMPEG` and `FFMPEG-SOURCE.md`; the Rust code is MIT-licensed.
The library also carries code under its own notices:

- Yoga (`LICENSE-YOGA`)
- Zig's runtime (`LICENSE-ZIG`)
- on Linux and Windows, LLVM's libc++, libc++abi, and libunwind (`LICENSE-LLVM`)
- on Windows, the MinGW-w64 runtime (`LICENSE-MINGW-W64`) and its gdtoa code (`LICENSE-GDTOA`)
- FFmpeg's zlib code (`LICENSE-ZLIB`)

Ship these notices with an app that links OpenTUI statically, or with `opentui.dll`.
Each release archive carries them too, with the notices of the library's other vendored code.

To link OpenTUI without FFmpeg, run `sh scripts/prepare-zig-deps.sh` and `zig build -Dvideo=false -Doptimize=ReleaseFast` in the native workspace.
Set `OPENTUI_LIB_DIR` to the absolute path of the resulting `lib/<artifact directory>` when you run Cargo.

## Windows consoles

On Windows, the app turns on the console's virtual terminal input and output, so the input parser reads the same sequences as on Unix.
Windows has no job control, so Ctrl+Z reaches key handlers instead of suspending the app.
Ctrl+Break, closing the console, logoff, and shutdown end `App::run` as signals do on Unix.
`TerminalView` runs programs on a pseudoconsole (ConPTY), and `pty::shell()` is `%COMSPEC%`.

See [C](/docs/native/c) for the native artifacts and how other languages link them.
