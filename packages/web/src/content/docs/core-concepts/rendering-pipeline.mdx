# Rendering pipeline

Changing a renderable requests a frame. `CliRenderer` advances the native scene, runs host hooks, and presents the resulting terminal output.
Application code does not receive a public diff object or dispatch every built-in draw.

This page follows the complete Core frame.
[How Core uses native](/docs/native/core) explains the bridge from renderables to native nodes with a working paint-hook example.
[Native rendering](/docs/native/overview) explains the native scene without the TypeScript integration.

## 1. Retained state becomes dirty

A renderable instance and its native scene node survive between frames.
Ordinary style and paint setters stage changes. Tree and resource operations use their own checked native calls.
Setters request a render when visual state changes.

Demand-driven scheduling coalesces repeated requests into a later frame. Continuous scheduling runs the same pipeline at the configured frame rate.

See [Renderer](/docs/core-concepts/renderer) for control states and scheduling.

## 2. The host runs frame callbacks

`CliRenderer.loop()` runs renderer-owned animation callbacks and then registered frame callbacks.
It awaits registered frame callbacks before scene painting.

It then calls `NativeScene.paint()`. That method runs relevant lifecycle work and flushes staged changes before native frame steps.

## 3. Native code prepares layout and painting

The native scene owns its Yoga nodes and calculates layout when necessary.
It prepares geometry, local sibling paint order, clipping, inherited opacity, and viewports.

Subscribed update, resize, and root-layout hooks run between native frame calls.
Native code repeats preparation when those hooks change layout, subject to the attempt's limits.
The host does not collect every node's computed layout to build a JavaScript render list.

Yoga uses a point scale factor of `1` for terminal-cell rounding.
Built-in text and editor measurement runs natively. A custom measurement provider uses a synchronous same-thread callback during Yoga.

See [Layout](/docs/core-concepts/layout) and [custom measurement](/docs/extend/custom-renderables#measure-intrinsic-size) for sizing and completed-layout reads.

## 4. The scene composes terminal cells

Native code paints built-in bodies into `nextRenderBuffer` in prepared order.
For a host paint hook, native code returns a request. JavaScript runs the hook, flushes its changes, and resumes the same frame.

A buffered custom renderable draws its own body into a private `OptimizedBuffer` before composition into the next buffer.
Buffering does not combine its entire child subtree into one surface.

The cell surface stores character or grapheme references, foreground, background, attributes, and image reservations. Read [Text and terminal cells](/docs/core-concepts/text-and-cells) for cell ownership.

After scene painting, `CliRenderer` runs whole-frame post-processing and then draws the console overlay.
Use the [Buffer API](/docs/reference/buffer-api) for checked drawing and scoped cell access.

## 5. Native code encodes and submits output

The native renderer compares current and next rows. It skips equal rows and compares remaining cells by character, colors, and full attributes.

For changed cells, native code emits cursor movement, color state, attributes, hyperlinks, and encoded text. It also handles cursor and mouse-pointer state.

`currentRenderBuffer` is encoder comparison state. It can change before output admission or presentation, so it is not a last-presented snapshot.
The encoder clears the next buffer after encoding.

An unchanged frame can emit no terminal bytes. A forced repaint, palette change, resize, or image transition can require broader output.

The Session owns the ordered output queue. Core copies output into a host-owned byte buffer and writes it to the configured `Writable`.

## 6. Output completion publishes the frame

The write callback acknowledges delivery of the copied output ticket.
When completed output reaches the frame's endpoint, native code publishes pending hit data, image metadata, and frame statistics.

Core then reconciles hover and emits its `frame` event.
This endpoint does not prove that a remote terminal visibly displayed the bytes.

Output pressure, scheduling yields, and terminal transitions can delay completion.
See [Frames and output](/docs/native/frames#commit-the-draft-then-complete-output) for admission, cancellation, and transport errors.

## Image protocol resolution

An image placement always has a block-cell fallback. Automatic protocol choice checks a configured override, Kitty support, Sixel support, then blocks.

Automatic Sixel also needs terminal pixel geometry. OpenTUI uses blocks until valid geometry arrives.

Capability replies arrive after renderer creation. An early frame can use blocks, then a later capability response can request a repaint with another protocol.

Automatic mode uses blocks under tmux because native graphics need pane-aware handling. Explicit protocol requests have different failure behavior.

See [Image](/docs/components/image) for fitting, protocol requests, tmux constraints, and Sixel limits. See [Terminal capabilities](/docs/reference/terminal-capabilities) for detection timing.

## Resize behavior

A resize does not rebuild the retained tree. Existing renderable instances remain attached with their current application state.

Native code checks and accepts new buffer dimensions before Core publishes the new renderer geometry.
The current and next buffer wrappers keep their identity and report the accepted dimensions.
The next layout pass uses the new dimensions. An active storage lease keeps old storage allocated but does not make it current.

Computed positions and sizes can change. Buffered renderables resize their frame buffers, then run resize hooks and listeners.

Image pixel geometry becomes unknown during resize. OpenTUI queries it again, so automatic Sixel can temporarily use blocks.

## Inspect frames

`currentRenderBuffer` and `nextRenderBuffer` are renderer-owned `OptimizedBuffer` values.
Access follows the active frame and storage-lease rules. Pending presentation can reject inspection.

`getRealCharBytes()` resolves cell characters to text. `getSpanLines()` groups current cells by colors and base attributes for diagnostics.

`getSpanLines()` uses native per-cell byte lengths to preserve multi-code-point graphemes and continuation cells.
It masks attributes to the low eight bits and exposes image fallback glyphs. Structured span capture therefore loses hyperlink and image identity.

Use character frames for visual text assertions and span capture for basic style diagnostics. Do not use span capture as a lossless buffer serialization.

See [Testing](/docs/core-concepts/testing) and [Rendering diagnostics](/docs/test-and-debug/rendering-diagnostics) for supported inspection tools.
